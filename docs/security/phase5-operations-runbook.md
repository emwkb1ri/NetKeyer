# NetKeyer Phase 5 Operations Runbook

Status: Active
Date: 2026-09-03

This runbook defines operational procedures for:

- TLS certificate rotation (nginx ingress)
- Signing key rotation (rendezvous JWT and grant secrets)
- Remote identity key rotation (desktop host/client secure transport identity)
- Security incident response

Use this with:

- `rendezvous_services/README.md`
- `security_plan.md`

## 1. TLS Certificate Rotation (nginx ingress)

### Scope

Applies when using:

- `docker-compose.yml` plus `docker-compose.nginx.yml`
- `nginx/certs/fullchain.pem`
- `nginx/certs/privkey.pem`

### Preconditions

1. Confirm current health is good:

Linux/macOS:

```bash
curl -fsS https://<host>/health
```

Windows PowerShell:

```powershell
Invoke-WebRequest -UseBasicParsing https://<host>/health
```

2. Confirm current certificate expiry window:

```bash
openssl x509 -enddate -noout -in nginx/certs/fullchain.pem
```

### Rotation Procedure

1. Acquire or renew certificate material.

For certbot deployment, use existing automation:

```bash
sudo certbot renew --deploy-hook 'cd /path/to/rendezvous_services && docker compose -f docker-compose.yml -f docker-compose.nginx.yml exec nginx nginx -s reload'
```

2. Update deployed files/symlinks at:

- `nginx/certs/fullchain.pem`
- `nginx/certs/privkey.pem`

3. Reload nginx without restarting services:

```bash
docker compose -f docker-compose.yml -f docker-compose.nginx.yml exec nginx nginx -s reload
```

### Verification

1. Verify TLS endpoint responds:

```bash
curl -fsS https://<host>/health
```

2. Verify expected certificate is served:

```bash
openssl s_client -connect <host>:443 -servername <host> </dev/null 2>/dev/null | openssl x509 -noout -issuer -subject -dates
```

3. Verify nginx logs do not show reload errors:

```bash
docker compose -f docker-compose.yml -f docker-compose.nginx.yml logs nginx --tail=200
```

### Rollback

1. Restore previous known-good `fullchain.pem` and `privkey.pem`.
2. Reload nginx again.
3. Re-run verification checks.

## 2. Rendezvous Signing Secret Rotation (JWT + Connection Grants)

### Scope

Applies to server-side auth settings:

- `RENDEZVOUS_JWT_SECRET`
- `RENDEZVOUS_CONNECTION_GRANT_SECRET`

### Impact

- Existing websocket connections continue until reconnect.
- New or reconnecting clients must present tokens signed by the active secret.
- Any outstanding connection grants signed with an old secret become invalid.

### Recommended Strategy

Use a planned maintenance window with a short reconnect expectation. During rollout, keep `RENDEZVOUS_SECURITY_STAGE` at `compat` only if a temporary compatibility window is explicitly required.

### Rotation Procedure

1. Generate new secrets from a CSPRNG and store in your secret manager.
2. Update deployment environment values:

- `RENDEZVOUS_JWT_SECRET=<new-value>`
- `RENDEZVOUS_CONNECTION_GRANT_SECRET=<new-value>`

3. Recreate rendezvous service container(s):

```bash
docker compose -f docker-compose.yml up -d --force-recreate rendezvous
```

4. Force clients to request new grants and reconnect.

### Verification

1. Confirm healthy startup and version:

```bash
curl -fsS http://127.0.0.1:49920/health
```

2. Monitor auth telemetry for abnormal spikes:

- `statistics.security_metrics.auth_failures`
- `statistics.security_metrics.handshake_failures`
- `statistics.security_metrics.replay_rejects`
- `statistics.security_metrics.decrypt_failures`

3. Confirm expected policy stage in startup logs.

### Rollback

1. Restore previous secret values.
2. Recreate rendezvous container.
3. Re-issue valid user tokens/grants from the previous secret source as needed.

## 3. Remote Identity Key Rotation (Desktop Host/Client)

### Scope

Applies to local secure transport identity files generated by desktop app:

- `%LOCALAPPDATA%/NetKeyer/security/remote-identity-host.json`
- `%LOCALAPPDATA%/NetKeyer/security/remote-identity-client.json`

### Impact

- Trust identity changes after rotation.
- Existing sessions are unaffected until reconnect.
- New sessions use the new identity key pair.

### Rotation Procedure (Windows)

1. Stop NetKeyer.
2. Backup current identity files:

```powershell
$root = Join-Path $env:LOCALAPPDATA 'NetKeyer\security'
Copy-Item "$root\remote-identity-host.json" "$root\remote-identity-host.json.bak" -ErrorAction SilentlyContinue
Copy-Item "$root\remote-identity-client.json" "$root\remote-identity-client.json.bak" -ErrorAction SilentlyContinue
```

3. Remove the identity file(s) to rotate:

```powershell
Remove-Item "$root\remote-identity-host.json" -ErrorAction SilentlyContinue
Remove-Item "$root\remote-identity-client.json" -ErrorAction SilentlyContinue
```

4. Restart NetKeyer and establish a remote session to regenerate keys.

### Verification

1. Confirm new identity files exist.
2. Confirm secure handshake succeeds (no fallback) and keying works.
3. Confirm latency telemetry remains within expected bounds.

### Rollback

1. Stop NetKeyer.
2. Restore `.bak` identity files.
3. Restart and re-test secure connection.

## 4. Security Incident Response

### Trigger Conditions

Start this procedure when you detect one or more:

- Unexpected spikes in `auth_failures`, `handshake_failures`, `replay_rejects`, or `decrypt_failures`
- Repeated unknown-client registration attempts
- Suspected leaked JWT/grant secret
- Suspected host/client endpoint compromise

### Immediate Containment

1. Reduce attack surface:

- Restrict network ACLs/firewall to trusted IP ranges.
- If needed, set `RENDEZVOUS_HEALTH_ACCESS_MODE=disabled` temporarily.

2. Move policy to stricter enforcement:

- `RENDEZVOUS_SECURITY_STAGE=strict`

3. Rotate server signing secrets (Section 2).

4. If endpoint compromise is suspected, rotate desktop identity keys (Section 3).

### Evidence Collection

1. Preserve logs before restart/cleanup:

```bash
docker compose -f docker-compose.yml logs rendezvous --tail=5000 > rendezvous-incident.log
docker compose -f docker-compose.yml logs relay --tail=5000 > relay-incident.log
```

If nginx overlay is enabled:

```bash
docker compose -f docker-compose.yml -f docker-compose.nginx.yml logs nginx --tail=5000 > nginx-incident.log
```

2. Record `/health` snapshot and timestamp.
3. Record active deployment config fingerprints (no plaintext secrets in reports).

### Eradication and Recovery

1. Patch root cause (config, token issuance path, ingress controls, or endpoint hygiene).
2. Redeploy clean services.
3. Validate:

- `/health` is stable
- telemetry counters stop climbing abnormally
- end-to-end secure host/client connection succeeds

4. Gradually return to target rollout stage if temporarily changed.

### Post-Incident Actions

1. Publish timeline and impact summary.
2. Document indicators and detection gaps.
3. Add or adjust automated alerts for security metrics.
4. Update this runbook and `security_plan.md` with lessons learned.

## 5. Minimum Monitoring and Alerting Signals

Monitor at least:

- `statistics.security_metrics.auth_failures`
- `statistics.security_metrics.handshake_failures`
- `statistics.security_metrics.replay_rejects`
- `statistics.security_metrics.decrypt_failures`
- Keying latency telemetry: handshake duration, p50 lag, p95 lag, max lag

Suggested thresholds (tune per environment):

- auth_failures increase > 20 in 5 minutes
- replay_rejects increase > 5 in 5 minutes
- decrypt_failures increase > 3 in 5 minutes
- keying p95 lag sustained above baseline + 5 ms for 10 minutes

## 6. Change Management Checklist

Before applying any rotation:

1. Confirm backups exist for replaced files/secrets.
2. Confirm rollback owner and command path.
3. Announce expected reconnect impact.
4. Validate post-change health and telemetry.
5. Capture change log entry with timestamp and operator.
